# samvil-publish (ultra-thin)

Adopt the **Issue Architect** role. Convert `project.seed.json` into a
structured GitHub Issues tree (1 Epic + N Tasks). Pattern adapted from
Ouroboros's `publish` skill — keeps the same shape so SAMVIL users
who switch between systems see consistent output. Solo developers use
this as personal kanban; teams use it for division of work.

## Prerequisites

1. `gh` CLI installed + authenticated. Check: `command -v gh && gh auth status`. Missing → tell user `Install gh from https://cli.github.com/` and stop.
2. `project.seed.json` exists in cwd. Missing → tell user `Run /samvil first to generate a seed.` and stop.

## Step 1 — Resolve target repo

`gh repo view --json nameWithOwner -q '.nameWithOwner' 2>/dev/null`. If detected → AskUserQuestion `["이 레포에 발행할까?"]` with options `[<detected_repo> / 다른 레포 지정]`. If not detected or user picks "다른 레포 지정" → ask `["owner/repo 형식으로 입력해줘"]`. Store as `$REPO`. **All gh commands MUST include `-R $REPO`.**

## Step 2 — Duplicate check

```bash
gh issue list -R $REPO --label "samvil" --state all --search "$(jq -r .name project.seed.json)" --limit 5 --json number,title,state
```

If matches found → AskUserQuestion `["같은 seed로 보이는 이슈 발견:\n<list>\n새로 만들까?"]` with options `[새로 만들기 / 취소]`. 취소 → stop.

## Step 3 — Plan issue structure

For each `seed.features[i]`, plan one Task issue (`[Task] <feature.name>`). Plan one Epic (`[Epic] <seed.name>`) that lists them. AskUserQuestion `["이 구조 OK?"]` with options `[발행 / 조정 필요]`. 조정 → ask user changes, redraft, re-present.

## Step 4 — Create labels (idempotent)

```bash
gh label create "samvil" -R $REPO --description "Created by samvil-publish" --color "6f42c1" 2>/dev/null || true
gh label create "epic" -R $REPO --description "Epic / parent issue" --color "0075ca" 2>/dev/null || true
gh label create "task" -R $REPO --description "Implementation task" --color "008672" 2>/dev/null || true
```

## Step 5 — Create Epic issue

```bash
EPIC_URL=$(gh issue create -R $REPO --title "[Epic] $(jq -r .name project.seed.json)" \
  --label "samvil,epic" --body "$(cat <<'BODY'
## Goal
<seed.description>

## Tech Stack
- framework: <seed.tech_stack.framework>
- 기타: <other tech_stack entries>

## Constraints
<- list per constraint>

## Out of Scope
<- list per out_of_scope>

## Evaluation Principles (v4.23+)
<table: principle | weight | rationale, if seed.evaluation_principles present>

## Exit Conditions (v4.23+)
<- list per exit_conditions, if present>

## Acceptance Criteria (summary)
<top-level AC count per feature>

---
**Seed**: `project.seed.json` (version <seed.version>) | **솔루션 타입**: <seed.solution_type>
*Generated by SAMVIL via `/samvil-publish`*
BODY
)")
EPIC_NUM=$(echo "$EPIC_URL" | grep -o '[0-9]*$')
```

## Step 6 — Create Task issues (one per feature)

For each feature: `gh issue create -R $REPO --title "[Task] <feature.name>"` with body listing the feature's `acceptance_criteria` as Markdown checkbox list, plus `Parent: #$EPIC_NUM`. Capture each issue number into `$TASK_NUMS[]`.

## Step 7 — Update Epic with task links

```bash
gh issue comment $EPIC_NUM -R $REPO --body "## Implementation Tasks
- [ ] #<task_1> — <name_1>
- [ ] #<task_2> — <name_2>
..."
```

## Step 8 — Summary

```
Published to $REPO:
  #<epic>  [Epic] <seed.name>
    ├── #<task_1>  [Task] <feature_1.name>
    └── #<task_N>  [Task] <feature_N.name>

View: https://github.com/$REPO/issues/$EPIC_NUM
```

Suggest next: `Track via GitHub Projects board, or run /samvil-build to implement tasks programmatically.`

## Anti-Patterns

1. NEVER skip Step 2 duplicate check — accidentally creating 8 identical Epics ruins a tracker.
2. NEVER write secrets into Issue bodies — strip `external_api_config.api_keys` and similar fields before embedding.
3. NEVER use `-R` flag value from a previous Step — re-derive from `$REPO` variable every command.
4. **`AskUserQuestion` 호출 포맷**: `questions=["<질문>"]` 배열만 허용; 문자열 직접 전달 시 `InputValidationError`.

## Chain

Terminal — no chain. SAMVIL pipeline (build/qa) continues independently if the user invokes those skills separately.
